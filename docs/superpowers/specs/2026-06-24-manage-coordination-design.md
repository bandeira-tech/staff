# manage-coordination — design

Status: design approved 2026-06-24. Plan to follow.

## Goal

Add `/cc-chat:manage-coordination <prose>` to the cc-chat plugin: a
slash command whose caller becomes a **manager** that spins up N
long-running subagent **participants** (each scoped to a folder or
file), facilitates an active cooperation toward a deliverable, and
closes the room when the user calls time.

The room is a worker room, not a committee. Default disposition for
participants is *do, don't ask*. The manager and the user steer; the
participants execute.

## Scope and non-scope

In scope:

- The slash command and the manager runbook
- A unified URI grammar across all of cc-chat
- Long-running participant subagents with a small state machine
- Room identity card (`meta.md`), pause/resume/end protocol,
  mention protocol, deliverable capture
- Configurable per-project participant tool budget
- Migration of existing cc-chat surfaces (commands, src/, web/,
  scripts/, docs/, tests/) to the unified grammar in one cut

Out of scope (v1):

- Adding a participant after the room is rolling
- Multi-rig coordinations
- Richer UI (clickable mentions, replay scrubbing)
- Per-participant cryptographic identity (single rig key suffices)

## Philosophical shift to call out

The current cc-chat README frames the convention as *present-leaning*,
TTL-buffered, "no archive." This design assumes a **persistent** rig
backend because `meta.md` and the deliverable (`output`) must be
readable by late-joining and re-dispatched participants and by the
user after the room closes. The README already names
`immutable://open/cc-chat/` as the default root, so persistence is
already the operational reality; this spec just makes it the stated
philosophy. Rooms are persistent worker rooms.

## URI grammar (unified)

One canonical shape:

```
<root>/<room>/<participant>/<type>/<ts>-<slug>.md
```

with one deliberate exception, the room's identity card:

```
<root>/<room>/meta.md
```

Segments:

- `<root>` — user-controlled rig namespace; default
  `immutable://open/cc-chat/`.
- `<room>` — `<ts>-<slug>` where `<ts>` is `YYYYMMDDhhmmss` UTC and
  `<slug>` is `[a-z0-9][a-z0-9-]{0,47}`. Either user-supplied (parsed
  from the prose) or auto-generated by the manager from the goal.
- `<participant>` — `[a-z0-9][a-z0-9-]{0,31}`. The manager is always
  `manager`. Other names default to scope-derived slugs (`src-auth`
  for `src/auth/`), overridable in the prose.
- `<type>` — closed set: `join`, `msg`, `pause`, `resume`, `end`,
  `mention`, `output`.
- `<ts>-<slug>.md` — leaf; `<ts>` is the message's own timestamp
  (distinct from the room's), `<slug>` is content-derived or a 6-char
  base32 nonce. `.md` suffix uniform across types.

Type-specific shapes and payloads:

| Type      | Path tail                                            | Payload         | Mintable by    |
|-----------|------------------------------------------------------|-----------------|----------------|
| `join`    | `<who>/join/<ts>-<nonce>.json`                       | `{"scope":"<path>","role":"<role>"}` (manager omits scope) | anyone in room |
| `msg`     | `<who>/msg/<ts>-<slug>.md`                           | markdown text   | anyone in room |
| `pause`   | `manager/pause/<ts>-<nonce>.md`                      | reason (one line) | manager only |
| `resume`  | `manager/resume/<ts>-<nonce>.md`                     | empty or note   | manager only   |
| `end`     | `<who>/end/<ts>-<nonce>.md`                          | empty or short leaving note (manager mints empty to close room; participants mint with leaving note) | manager closes room; participants close themselves |
| `mention` | `<from>/mention/<target>/<ts>-<slug>.md`             | markdown text   | anyone in room |
| `output`  | `manager/output/<ts>-<slug>.md`                      | deliverable artifact (markdown default) | manager only |

`validate(uri)` enforces alphabet, type-is-in-closed-set, and the
manager-only constraint for `pause`/`resume`/`output`/room-closing
`end`.

Subscription patterns:

- Participants open:
  - `<root>/<room>/*/msg/**` — everyone's messages
  - `<root>/<room>/manager/pause/**` and `.../resume/**` and
    `.../end/**` — control
  - `<root>/<room>/*/mention/<self>/**` — being called by name
  - `<root>/<room>/*/join/**` — know who's in the room
  - `<root>/<room>/manager/output/**` — see the deliverable
- Manager opens `<root>/<room>/**` — everything.

(If the underlying rig MCP cannot honor multi-glob subscribes with
type-aware wildcards, participants subscribe to `<root>/<room>/**`
and filter client-side. See verification list at the bottom.)

## Lifecycle

### Manager (the calling agent)

1. **Parse prose → plan.** Extract goal, kind of cooperation
   (informal, only used to shape facilitation), participants
   (scope + optional name + optional role), room name (if given),
   deliverable destination (default `./.cc-chat/<room>/output.md`
   + chat post; overridable by prose).

   Pre-flight scan per CLAUDE.md: if goal/participants/deliverable
   destinations are ambiguous or in conflict, surface **one** batched
   `AskUserQuestion` before doing anything.

2. **Tool-budget check.** Read `.claude/cc-chat.local.md` for
   `participant-tool-budget`. If absent, surface a three-choice
   `AskUserQuestion`:
   - *read-only + chat* (default for this run)
   - *full access, this run*
   - *full access, always* (persisted)

3. **Mint `<root>/<room>/meta.md`.** The room now exists, with all
   its context. Single immutable file; never updated. If something
   needs to change mid-room, the manager posts a `msg`.

4. **Manager joins.** Mint `manager/join/<ts>-<nonce>.json` with
   `{"role":"manager"}`. Open subscription `<root>/<room>/**`.

5. **Spawn participants.** All in one tool message,
   `run_in_background: true`, so they run concurrently. Per-call
   prompt assembled from the inlined participant template (see
   below) + identity/scope/role for that participant.

6. **Facilitate.** Loop:
   - read recent deliveries
   - decide whether to intervene:
     - someone is being talked past → `@<name> <question>` (mint to
       `manager/mention/<target>/...`)
     - room converging on a wrong assumption → corrective `msg`
     - diminishing returns hit → mint `pause` with a reason, surface
       to the user via the chat conversation
     - a participant has gone quiet too long → optionally
       re-dispatch them, or @-mention them
   - the user can speak any time: through the manager (manager
     relays as `[user] ...` in a `msg`), through the web UI as their
     own participant, or via `scripts/say.ts`

7. **Pause / resume.** Manager mints `pause` when it decides;
   `resume` when ready to continue (typically after user input).
   While paused, only the manager talks (usually to pose a question
   to the user). Participants honor `pause` by finishing any
   in-flight thought, posting it, then going silent.

8. **End conditions.**
   - **User calls time** ("ok wrap it up" / `[END]` / direct
     instruction). Manager mints `manager/end/<ts>-<nonce>.md`
     (empty). Participants honor it.
   - **Manager believes ready, asks user.** Manager mints `pause`,
     asks via chat "I think we're ready to draft — proceed?". On
     approval, proceeds to step 9.
   - **Stuck / no progress.** Manager mints `pause`, surfaces to
     user; user chooses re-dispatch / change-question / end.

9. **Draft deliverable.** Manager reads the room via `b3nd_read`
   over `<root>/<room>/**`, synthesizes per the spec in `meta.md`'s
   `deliverable` field, **writes the file** at the destination
   (default or overridden), and **posts** the same body as
   `manager/output/<ts>-<slug>.md`. Chat record and working-tree
   file match byte-for-byte.

10. **Close the room.** Mint `manager/end/<ts>-<nonce>.md` if not
    already. Report back to the user: deliverable path, room URI for
    replay, brief summary of what happened.

Manager bookkeeping: appends to `./.cc-chat/<room>/ledger.md` as the
room progresses — participants, dispatch decisions, re-dispatches,
pause reasons, context-build-up timings (derived from
`join → first-msg` URI timestamps). One task, one ledger line per
CLAUDE.md.

### Participant (each dispatched subagent)

The participant template is inlined in
`plugin/commands/manage-coordination.md` (no separate
`plugin/agents/` file). Per-call the manager interpolates:
room URI, participant name, scope path, role, tool budget,
re-dispatch preamble (if any).

```
You are a participant in a cc-chat coordination.

Identity
- Room: <root>/<room>/
- Your name: <participant>
- Your scope: <path>
- Your role: <one line>

Tool budget: <read-only-chat | full-this-run | full-always>

Step 1 — JOIN.
Mint <root>/<room>/<you>/join/<ts>-<nonce>.json with
{"scope":"<path>","role":"<role>"}. Open subscriptions
(see list below). You are now in the room.

Step 2 — BRIEF.
Read <root>/<room>/meta.md. That's the room's brief: goal,
participants, deliverable, rules.

Step 3 — INITIATIVE.
Post your first msg. Two flavors:
- If the brief named work for you: "ok, looking into <x of my
  scope>" / "starting on <thing>"
- If the brief left it open: "seems related to <subset of my
  scope> — I'll <plan>" or "I lead on <topic>, watching for
  <signal>"

Step 4 — ACTIVE.
Get to work. Continuously listen to the room. Balance doing
vs listening as the moment requires:
- have work to do → do it (no permission needed)
- someone's doing something that affects you → react
- you have information another participant needs → share it
- you're lead on a thread → drive it

Post msgs as work happens: "starting X", "found Y",
"committed on branch Z", "blocked on W". To call a specific
participant, mint
<you>/mention/<target>/<ts>-<slug>.md with the question or
ask as the markdown body.

State machine:
  ACTIVE — default. Speak and act when the moment calls for it.
  PAUSED — on manager/pause/**, stop initiating. Finish any
    in-flight thought and post it, then stay silent. Keep
    observing. On manager/resume/**, return to ACTIVE.
  ENDING — on manager/end/**, post a final msg if you have
    one, mint <you>/end/<ts>-<nonce>.md with a short leaving
    note, exit.

Subscriptions
  <root>/<room>/*/msg/**
  <root>/<room>/manager/pause/**
  <root>/<room>/manager/resume/**
  <root>/<room>/manager/end/**
  <root>/<room>/*/mention/<you>/**

Constraints
- Don't mint outside <root>/<room>/<you>/.
- Don't mint type=pause, type=resume, or manager-closing
  type=end. Those are manager-only.
- Don't draft the deliverable. The manager produces output.
- If your tool budget permits mutation and the coordination
  needs you to create/edit/commit, do it. Branch when in
  doubt — git checkout -b cc-chat/<room>/<you>. Post a msg
  describing what you're about to do, do it, post the result
  (include commit SHA when relevant).

Failure modes
- Rig unreachable: do not try to post; return from this
  Agent call with a structured stdout/return:
    {"status":"exit_no_rig","last_state":"...",
     "uncommitted_work":"...","branch":"..."}
  The manager will help the user troubleshoot and may
  re-dispatch you. You will receive a "you were here before"
  preamble; catch up via b3nd_read on the room.
- Agent call nearing timeout: post a checkpoint msg, mint
  your <you>/end with a "timing out, may be re-summoned"
  note, exit.

Disposition: do, don't ask. The brief and your scope are
your authority. The manager and user steer.
```

## `meta.md` shape

Markdown with frontmatter:

```
---
room: <ts>-<slug>
created: <ISO-8601 UTC>
manager: manager
tool_budget: read-only-chat | full-this-run | full-always
deliverable:
  shape: <free-form description from prose>
  file: ./.cc-chat/<room>/output.md
  chat_uri: <root>/<room>/manager/output/
participants:
  - name: <participant>
    scope: <path>
    role: <one line>
  - ...
---

# Goal

<lightly-normalized goal from the user's prose>

# Rules of the road

- @<name> to call on a participant directly.
- Manager signals pause / resume / end by minting `pause`,
  `resume`, `end` URI types — honor them.
- Worker-room defaults: do, don't ask. Within your scope and
  tool budget, execute.
- Branch when speculative: cc-chat/<room>/<you>.

<any extra pointers from the prose>
```

`meta.md` is minted once, immutable.

## Risks and open decisions

- **Convention migration risk.** Every existing cc-chat consumer
  (web UI, tail, scripts, skill) breaks the moment the new grammar
  lands. v1 cuts over cleanly; no compatibility shims. Acceptable
  because cc-chat is pre-1.0 and we own all the consumers. We
  re-run the existing demo end-to-end to confirm no visual
  regression.

- **Subagent call duration.** Each participant is one Agent call;
  Claude Code subagent calls have an effective ceiling. Mitigation
  baked in: structured exit on rig-down / timeout, manager
  re-dispatches with a "you were here before" preamble. Practical
  ceiling discovered only in real sessions; ledger telemetry will
  help.

- **Convergence risk.** Worker rooms without a pre-decided
  termination can drift. Mitigations: user calls time explicitly,
  manager pauses on diminishing returns, ledger tracks pause
  reasons. If rooms routinely drift, future tweak: optional soft
  deadline in `meta.md`.

- **Cost.** N participants × Agent-call duration × token rate.
  v1 has no caps; only knob is "spawn fewer participants." If
  painful, future: participant token budget honored from `meta.md`.

- **Verification surface.** Room quality is qualitative;
  deliverable file is the obvious check. Web UI on a single-room
  URL is the primary instrument; ledger captures the rest.

- **Cooperation-vs-discussion drift.** Easy slip in docs and
  prompts. Keep the worker-room framing front-and-center in the
  skill and the participant prompt's "do, don't ask" line.
